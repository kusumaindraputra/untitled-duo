# Web Performance Pass — Floor 3 and Cipher Keeper Phase 4 (beta plan 4.3)

**Date:** 2026-09-27 · **Build:** Godot 4.6.2, Web export preset (Compatibility, no threads)
**Decision record:** docs/architecture/adr-0050-web-performance-bullet-budget-and-batching.md

## Verdict

The web build missed the budget in the busiest fight, and it now meets it on the CPU side.

- **Keeper phase 4 (Tempest), CPU only:** 48.8 fps average with a 77 ms p99 frame,
  49 frames over 33 ms in 15 s. It is now a steady 60.0 fps with a 22 ms p99 and no frame
  over 33 ms. The physics step went from 13.7 ms to 3.8 ms per frame.
- **Draw calls:** Floor 3 used 232 on average (peak 271) and Keeper phase 4 used 228
  (peak 272), both over the 200 budget. They now use 119 (peak 144) and 98 (peak 109).
  240 bullets on their own went from 1,387 draw calls to 1.
- **Bullet cap:** the densest fight peaked at 117 live bullets. The cap is set to 240
  (`BulletHellTuning.max_live_bullets`), so it never changes a current pattern. It only
  catches stacked elites, Cursed rooms and Hard mode.

**Not measured here:** real GPU frame time. This container has no GPU, so Chromium draws
WebGL through SwiftShader on the CPU, and every build runs at 2–4 fps with rendering on.
Those rows are kept for the draw-call counts only. A check on a real low-end laptop
(Chrome, integrated GPU) is still needed before the beta, and it belongs in 4.5 or 5.3.

## How it was measured

`tools/perf/PerfProbe.tscn` loads main.tscn, starts a run, jumps to Floor 3 and plays a
bot. Fayde circles the arena, casts three times a second and has god mode on. The probe
prints one `PERF_RESULT` JSON line at the end.

- **floor3:** a normal Floor 3 combat room with its full wave and reinforcements.
- **keeper_p4:** a Floor 3 boss room with a forced variant. The Keeper is dropped just
  under its lowest phase threshold, so every pattern layer and phase hazard is active (the
  HUD shows PHASE 4), and it is healed back to that line so it never dies mid-sample.
- **bullets:** n bullets kept in flight with nothing else running, to isolate per-bullet cost.
- **render=0** turns off RenderingServer's render loop. The frame time is then the game's
  CPU time in WebAssembly, which is what a player's browser runs whatever their GPU is.

The web builds were exported with the probe as the main scene (the release template does
not allow a scene override), served locally and run in headless Chromium 1194 at 1152×648,
with a 3 s warm-up and a 15 s sample (10 s with rendering on). "Before" is main at 84cc1eb
and "after" is this branch. Rooms and waves are random per run, so bullet counts differ
between rows.

## What was slow, and the fix

| Hotspot | Evidence | Fix (ADR-0050) |
|---|---|---|
| Every bullet redrew every frame | 240 bullets: 7.8–10.4 ms physics per frame natively, down to 2.4–2.7 ms with gating | `Projectile.needs_redraw()`: redraw only while the trail grows, a homing bullet turns, or the bullet fades out |
| Bullets did not batch | Web: about 5.8 draw calls per bullet (1,387 for 240) | `BulletArt` bakes the bullet into a texture once; each bullet is 4 textured quads that batch |
| Room edges were ~200 nodes | 207–246 visible Polygon2D and 45–59 Line2D per room, one draw call each | `QuadBatch`: rim ledge and platform edge are one node each |
| No upper bound on bullets | Peak 117 in the densest fight | `max_live_bullets = 240` in bullet_hell_tuning.tres |

FloorLighting (ADR-0043) is not a hotspot. In a native run of the same probe, a Floor 3
room drew 110 draw calls with lights off and 111 with lights on. Its light pools are
fixed in size.

## Re-running

```
# native, CPU only
godot --headless --path . res://tools/perf/PerfProbe.tscn -- scenario=keeper_p4 variant=tempest seconds=15
# web: set run/main_scene to res://tools/perf/PerfProbe.tscn, export the Web preset, restore it,
# then open index.html?scenario=keeper_p4&variant=tempest&render=0 and read PERF_RESULT in the console
```
Options: scenario (floor3, keeper_p4, bullets), variant (tempest, fractured, gilded),
seconds, warmup, lights (0 = off), outline (1 = high-contrast bullets), render (0 = CPU
only), n (bullets scenario), shot (PNG path).
